# Phase 21 — Queue Overview UI

> Status: ✅ Complete. Git tag: `v1.9.0`.
> Built in three parts: 21a backend, 21b frontend, 21c cancellation and data safety.

**Why:** status is only visible per-episode today (SSE on that episode's view). With more than a couple of episodes ingesting, there's no single place to see what's waiting, what's running, what finished — including what finished while you were away — and what failed or looks stuck. Promoted from `FUTURE_SCOPE.md` 2.1b.

**Scope:** transient, at-a-glance status — not an audit log. Two surfaces read from one endpoint: a dedicated queue page (full detail, fixed recent window) and a header popover ("widget") opened from an activity icon (first few per group, less detail, "(N) more…" links to the page). Backend (21a) is built and verified before frontend (21b) starts; both ship together as `v1.9.0`.

**Design notes:**
- **Two timestamps: `queued_at` and `status_changed_at`.**
  - `queued_at` — when the user requested ingestion (the `QUEUED` transition; reingest overwrites it). Preserves request order even when the worker isn't running 24x7, so the gap between request and pickup shows up as time spent in Queued.
  - `status_changed_at` — written only when `pipeline_status` actually changes. Download progress writes (1% increments) must not bump it, or rows would churn. For `READY`/`ERROR` it *is* the finished time, so 2.1b's `finished_at` is dropped as redundant. For an active stage, it drives the stuck indicator.
  - `updated_at` is not used by the queue UI and is not part of this phase.
- **Groups and ordering:**
  - **Queued** = `QUEUED`, ordered by `queued_at` (next up first).
  - **In progress** = `DOWNLOADING`, `TRANSCRIBING`, `DIARIZING`, `INFERRING_SPEAKERS`, `CHUNKING`, `EMBEDDING`, ordered by pipeline stage in that sequence (a single backend constant), then by `queued_at` within a stage. Forward vs. reverse stage order is decided later — only the constant changes.
  - **Finished** = `READY`, ordered by `status_changed_at` descending.
  - **Error** = `ERROR`, ordered by `status_changed_at` descending.
  - `PENDING` (never ingested, or reset) is never included.
- **Relative order, no position number.** Ordering comes from Postgres only — `IngestionQueue` still exposes no position/ordering (ARCHITECTURE.md 3.4). `MAX_CONCURRENT_INGESTIONS` and streaQ retry ordering are deliberately ignored; revisit only if rows visibly jump around. `PipelineStatusUpdate.position` exists but is unused — left alone in this phase.
- **Full list by default, UI-side limiting.** Without `limit`, every group returns all matching episodes; the widget slices what it displays. `limit` is optional and caps `items` per group when given. Every group also returns `total` (the list length when unlimited; a per-group `COUNT` using the same condition when `limit` is given) so "(N) more…" works either way.
- **`since` applies to Finished and Error only.** Queued and In progress are never time-filtered.
- **Possibly stuck (display-only warning).** An active-stage episode (DOWNLOADING through EMBEDDING) is flagged `possibly_stuck` when `now − status_changed_at` exceeds that stage's threshold. Thresholds are per stage and generous for DOWNLOADING (slow, rate-limited hosts), live in `Settings`, and are computed server-side so the same rule gates `/reset`. `QUEUED` is never flagged — waiting on an offline worker is expected. Actually marking an episode dead stays with 2.1g. Defaults (minutes): DOWNLOADING 60, TRANSCRIBING 45, DIARIZING 20, INFERRING_SPEAKERS 15, CHUNKING 10, EMBEDDING 15 — set against an observed server p99 of ~27 min for a whole >1h episode, and erring loose since a too-tight threshold unlocks `/reset` on a live job. Each is overridable via `STUCK_THRESHOLD_<STAGE>_MIN`; all stay below `STREAQ_TASK_TIMEOUT`. TRANSCRIBING/DIARIZING include time spent waiting for a `ProcessPoolExecutor` slot.
- **API reset vs. UI clear — two separate operations:**
  - **`POST /api/v1/episodes/{episode_id}/reset` changes the backing data.** It replaces `DELETE /api/v1/episodes/{episode_id}/transcript` and wraps Phase 11's `delete_episode_transcription()`, renamed `reset_episode()`: bulk-deletes chunks/segments/speakers, sets `PENDING`, clears pipeline fields. This one operation returns an errored, stuck, finished, or queued episode to its initial state, which also removes it from the queue view. An action sub-resource (`POST …/reset`) matches the existing `/ingest`, `/reingest`, and `/refresh` endpoints; `DELETE /episodes/{id}/ingestion` was considered as the more REST-pure alternative.
    - Allowed from `READY`, `ERROR`, `QUEUED`, or an active stage flagged `possibly_stuck`.
    - `409` from an active stage that isn't flagged. Asyncio-level cancellation of a running job works, but a Whisper subprocess keeps running unobserved (2.1a), so resetting live work is deliberately not offered yet.
    - Reset is a compare-and-set: the `UPDATE` only applies if the status and `ingestion_job_id` are still what the handler observed (`IS NOT DISTINCT FROM`, so a `NULL` job id matches). A mismatch returns `409` and touches nothing — for a "stuck" episode, that's how a still-alive worker reveals itself. Only after a successful reset does the handler call `IngestionQueue.cancel()` for `QUEUED`/stuck episodes; cancelling first would abort a job for nothing whenever the compare-and-set then failed. Cancellation is best-effort: `StreaqQueue` aborts queued or running jobs via `Worker.abort_by_id()`; `BackgroundTaskQueue` can only cancel a job that hasn't started, and its job records are in-memory. A `QueueConnectionError` from `cancel()` is logged, not surfaced — the reset already committed and the job no longer owns the episode.
  - **Widget "Clear" is view-only.** It stores `now()` in a cookie; the widget then shows only Finished and Error episodes with `status_changed_at` after that value. Clearing hides errored episodes from the widget without resetting them. No server state changes, so in the password-protected demo deployment one viewer's clear doesn't affect anyone else. The queue page is unaffected.
  - **Errored episodes get two actions:** *Retry* (the existing reingest — back into the queue) and *Reset* (`/reset` — back to `PENDING`, leaves the queue view).
- **`ingestion_job_id` identifies the job that owns an episode.** Only the job whose id matches `episodes.ingestion_job_id` may work on that episode. At pickup, the worker compares its own job id to the episode's and exits without doing work on a mismatch. That covers a job reset while queued (the id is now `NULL`) and a job superseded by a later reingest (the id is now the new job's). A streaQ crash retry re-delivers the *same* job id, so it still runs. Every worker status write is also conditional on the id still matching, so a superseded or cancelled job's writes — including the shielded `ERROR` write `ingest_episode` makes on cancellation — become no-ops. For this to hold, the id must be committed with `QUEUED` *before* the job is submitted, which needs a small `IngestionQueue` Protocol change (see task 2). Inside the pipeline, ownership is also checked at every stage boundary (`enter_stage`: the status write itself returns `False` for a non-owner) and immediately before each data write (`may_write` → `PipelineStatusService.still_owns()`: transcript save, speaker names, chunk upsert), so a job that loses ownership mid-stage stops before writing anything further. `run_ingest` binds the status writer to the job with `PipelineStatusService.for_job(job_id)` on a copy of `PipelineServices` (`dataclasses.replace`), never mutating the caller's object.
- **The queue page shows the queue, not history.** Queued and In progress are always shown in full; Finished and Error only within a fixed recent window (24 h by default; callers may pass their own `since`). There's no timeframe filter on the page — browsing ingestion history is a separate concern. Both the widget and the page use one TanStack query (one key, one poll). The client sends no `since`: the backend's 24 h default is recomputed on every request, so the window slides with each poll and the query key stays the constant `['queue']` — a `now()` computed per render in the key would change it every render and refetch constantly. The widget narrows the shared data client-side with TanStack's `select`, keeping Finished/Error items after its cleared-at cookie; the page shows the full window.
- **Errors carry their message.** `pipeline_error` is returned with the episode data. Raw messages suit an owner-user but not an end user (e.g. the demo deployment). Mapping known causes to user-facing text (e.g. HTTP 403 → "download blocked") is an open decision, not part of 21a.
- **Only `READY` means an episode's data is complete.** A run interrupted while it still owns the episode (cancel, timeout, error) keeps whatever it already wrote — e.g. transcript and speakers from after diarization — and ends `ERROR`. The next Retry or Reset wipes that before doing anything else. `GET /transcript` and all three speaker routes return `409` unless the episode is `READY` (`src/api/episode_guards.py`). Chunks — the only data chat retrieval reads — are written in one upsert at the end of a run, so an interrupted run never leaves searchable content.
- **Updates are polled, not streamed.** The frontend polls via TanStack Query `refetchInterval` (paused in background tabs by default). A combined SSE stream was considered: it would do the same server-side DB polling the per-episode stream already does, while holding a long-lived connection per tab — and the header icon is on every page — in the same ~6-per-host budget that `EpisodeRow`'s per-row SSE connections use. The query function doesn't depend on delivery, so an SSE wrapper can be added later without reworking it. The icon's "anything in progress?" state comes from the Queued + In progress `total`s.
- **`pipeline_stage` is removed.** It's effectively unused; `pipeline_progress` stays in the DB for DOWNLOADING, but is no longer shown in the UI or returned by the queue endpoint.
- **Backfill:** existing rows get `NULL` for both new columns. Existing `READY`/`ERROR` episodes won't appear until they next change status, and existing active episodes can't be flagged stuck; accepted for now.

**Known limitations:**
- A run interrupted while it still owns the episode keeps its partial output (transcript/speakers) until the next Retry or Reset — by design; see "Only `READY` means complete" above.
- A Whisper subprocess keeps running after its job is cancelled or superseded (2.1a); its result is discarded.
- `BackgroundTaskQueue` (no-Redis fallback) can't cancel a running job; a reset stuck in-process job relies on the ownership checks alone.
- Audio files are named per episode, so a Retry reuses a previously completed download — see `FUTURE_SCOPE.md` 2.1i.
- `possibly_stuck` covers only the six active stages. An episode left in `QUEUED` by a job that died before `run_ingest` started (e.g. a worker-side crash or a task-registration bug) is never flagged — `QUEUED` legitimately means "waiting behind other work", so a fixed threshold would raise false alarms. Recovery is manual: Reset (allowed for `QUEUED`) from the episode kebab or `POST /episodes/{id}/reset`, then ingest again.
- An ownership lock outlives its worker only if the DB connection vanishes without closing (host freeze, VM suspend, network partition) — Postgres releases it once TCP keepalive gives up (~2h by default). Process exits of any kind (exception, SIGINT, OOM, `kill -9`) close the socket and release it immediately. Until then a reset of that episode fails fast with `409` after the 5s lock timeout. Backstop if ever needed: `idle_in_transaction_session_timeout` on the worker's DB role, or lower `tcp_keepalives_*`.

**Out of scope:** numeric queue position, backfilling the new columns, audit/history, a combined SSE queue stream.

**Tasks — 21c Cancellation and data safety** (✅ all complete). Supersedes the reset rules in 21a task 4 and 21b tasks 6 and 8.

4. ✅ Status stream ends on `PENDING` as well as `READY`/`ERROR`. `useEpisodeStatus(episodeId, cachedStatus)` streams only while the cached status is active and returns only the open stream's value — fixes rows/pages showing a stale stage after a cancel, and a stale `READY` after a re-transcribe.
