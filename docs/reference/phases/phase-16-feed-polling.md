# Phase 16 — Automatic Feed Polling

## What was built
- `src/ingestion/feed_poller.py` — new module. `poll_all_feeds(db)` loops every feed, calls the existing `feed_service.refresh_feed(feed_id, db)` per feed (unchanged — same function `POST /feeds/{feed_id}/refresh` already used), and returns a `PollResult` (`feeds_checked`, `new_episodes`, `errors`). Catches broad `Exception` per feed (not just `ValueError`) and calls `await db.rollback()` before continuing, so one bad feed can't leak half-committed state into the next feed's transaction or take down the rest of the poll. No ingestion, no queue involvement — refresh only.
- `scripts/feed_polling.py` — new CLI wrapper. Opens its own session via `AsyncSessionLocal` (`src/shared/db.py` — note: that file's own header comment still says `# src/db.py`, stale from before it moved; harmless but worth fixing eventually), calls `poll_all_feeds`, logs a summary via `logging.basicConfig` (required — without it, `logger.exception` calls inside `feed_poller.py` go nowhere when run standalone outside uvicorn's logging setup). Always exits 0 unless the DB itself is unreachable (that exception is intentionally left uncaught). Must be run with `PYTHONPATH=.` — running a script directly puts its own directory on `sys.path`, not the project root, so `src` isn't importable otherwise. Same fix already existed for `scripts/create_test_db.py`.
- `entrypoint.sh` — added `PYTHONPATH=. uv run scripts/feed_polling.py` in the server (`else`) branch only, before starting uvicorn. Not run in the worker branch — polling has nothing to do with worker's job. Relies on `scripts/feed_polling.py` always exiting 0 (except on total DB failure) to compose correctly with the script's `set -e`.
- `backend/Dockerfile` — added `COPY scripts/ ./scripts/` (previously missing entirely; `scripts/create_test_db.py` had the same latent gap, just never hit because that script isn't run in the container).
- `backend-README.md` — dev command changed to `PYTHONPATH=. uv run scripts/feed_polling.py && uv run uvicorn src.api.main:app --reload --port 3001`; new "Automatic Feed Polling" section documents the cron invocation.
- No `docker-compose.yml` changes. `backend`'s default `CMD` (`./entrypoint.sh`, no arg) already routes through the modified `else` branch — polling belongs in the Dockerfile/entrypoint layer (what happens when the container starts), not duplicated into compose (orchestration only).
- No new DB tables, no new config/env vars.

**Also landed in this same working session, unrelated to this phase:** `backend/Dockerfile` build fixes for Senko (added `gcc g++ python3-dev cmake ninja-build git` to apt packages; moved Senko to a `diarization` uv dependency group skipped in the main `uv sync` step, then installed via `uv pip install git+https://github.com/narcotic-sh/senko.git` directly, since the Mac-generated `uv.lock` entry didn't work in the Linux container). Bundled here because it touched the same file in the same sitting — not part of this phase's design and not covered by `ARCHITECTURE.md`/`FUTURE_SCOPE.md` updates.

## Decisions made
- **No `auto_ingest` flag, anywhere.** Considered and explicitly rejected — auto-triggering transcription on poll would be expensive on both a local dev machine (many feeds, some daily, all wanting Whisper+Senko at once) and a remote transcription provider (unbounded billed minutes). Refresh and ingestion stay fully decoupled; a newly discovered episode is left `PENDING`, identical to today's manual-refresh behavior. No new episode/feed state was needed for this reason.
- **No IngestionQueue/Redis involvement.** Feed refresh is I/O-bound (RSS fetch + small DB writes), not the CPU/GPU-bound long-running work the existing queue exists for. Routing refresh through it would reintroduce a Redis dependency this feature doesn't need and contend with `PIPELINE_MAX_WORKERS` capacity meant for real transcription.
- **Serial, not concurrent, per-feed refresh.** `asyncio.gather()` was considered; rejected for now as premature optimization given current low feed counts. The correct future shape, if revisited, is fetch-concurrently-then-persist-serially (network fetch is stateless and safe to parallelize; only the DB-writing step needs a single session) — not N concurrent `AsyncSession`s, which SQLAlchemy doesn't support safely.
- **`--reload`-safe by construction, not by a debounce mechanism.** Originally scoped a `last_polled_at` DB-backed debounce table to prevent uvicorn `--reload` from re-polling on every file save. Dropped once the dev command became `uv run scripts/feed_polling.py && uvicorn --reload ...` — `--reload` only restarts the uvicorn subprocess, never re-runs the shell command that launched it, so the problem doesn't exist in this shape at all. No debounce state needed.
- **Cron uses `docker compose run --rm --no-deps`, not `exec` into the running `backend` container.** `exec` would couple cron to `backend`'s uptime; `run --rm` is a self-contained one-off container from the same image, independent of whether `backend` is currently healthy. `--no-deps` specifically prevents this from starting `redis` (which polling doesn't need) via `backend`'s `depends_on`. `--rm` avoids unbounded accumulation of stopped containers (roughly 1,400/month at a 30-minute interval) — it does not save build time, since the image is already built and cached regardless.
- **Deploy target is host cron via SSH access to a self-managed VM**, not a Docker Compose profile-gated sidecar container. Confirmed the project's compose file has no `profiles` mechanism at all despite `ARCHITECTURE.md` referencing one — that's pre-existing doc drift, unrelated to this phase, not yet fixed at the time of writing.

## Done-when criteria
- `uv run scripts/feed_polling.py` (with `PYTHONPATH=.`) runs to completion against a real DB, refreshing every existing feed and logging a summary, without needing Redis or the worker to be running.
- A single malformed/unreachable feed does not prevent other feeds from refreshing, and does not leave orphaned pending rows in the session for the next feed's commit to pick up.
- `entrypoint.sh` polls once per container start in server mode, not in worker mode, and a feed failure does not prevent uvicorn from starting.
- The dev command (`uv run scripts/feed_polling.py && uv run uvicorn ...`) does not re-poll on `--reload` restarts, only on a genuine new invocation of the command.
- No `IngestionQueue`/Redis dependency introduced; no auto-ingest behavior added anywhere.
