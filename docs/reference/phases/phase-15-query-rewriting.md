# Phase 15 — Query Rewriting

> Moved from IMPLEMENTATION_PLAN.md. Status: ✅ Complete. Git tag: `v1.4.0`.
> See IMPLEMENTATION_PLAN.md's Phase Overview table for the one-line summary; see `docs/reference/architecture/query-engine.md` for current detail.

**Goal:** Ship Future Scope 1.3. Resolve conversation-dependent queries (pronouns, implicit topic references) into a self-contained, retrievable phrase before retrieval, so follow-ups like "what does he think about that?" don't produce multi-round tool calling against low-similarity results.

### 15.1 QueryRewriter (`src/query/query_rewriter.py`)
New class, `QueryRewriter(llm_client: LLMClient, timeout_seconds: float = QUERY_REWRITE_TIMEOUT_SECONDS)`. `rewrite(session, user_message) -> str` builds a prompt containing a plain-text, role-labeled summary of prior conversation turns (`_format_history()` — filters `session.messages` down to `user`/`assistant` entries with string `content`, dropping tool-call and tool-result messages entirely) plus the current message, and asks the LLM to either rewrite it into a self-contained search phrase or return it unchanged if it's already specific. Structured JSON output (`{"rewritten_query": "..."}`), `temperature=0.0`, same idiom `SpeakerResolver` uses for structured inference calls. Never raises: timeout (own configurable timeout, default 15s, separate from `LLM_REQUEST_TIMEOUT_SECONDS`), malformed JSON, a missing/empty/non-string `rewritten_query` field, or any other LLM-call exception all fall back to returning `user_message` unchanged, logged as a warning.

### 15.2 Engine wiring (`src/query/engine.py`)
`QueryEngine.__init__` gains a required `query_rewriter: QueryRewriter` parameter. In `chat()`, `rewrite()` is called once per turn, before `user_message` is appended to `session.messages` — so `_format_history()` only ever sees turns prior to the current one. The rewritten text is substituted into the LLM-facing message list only on `round_num == 0`, and only via constructing a new dict for that list slot (`messages[-1] = {**messages[-1], "content": rewritten_query}`) rather than mutating in place — `PromptBuilder.build_messages()` returns `[system] + session.messages`, i.e. the same dict objects `session.messages` holds, so an in-place mutation would have silently corrupted persisted conversation history. `session.messages` therefore always retains the user's literal original wording; the rewrite is single-turn scratch material with no persisted effect and cannot compound across turns. `chat.original_query` and `chat.rewritten_query` are logged as new attributes on the existing `chat` span (not on `retrieval.query`, which already reflects the tool-calling LLM's own composed argument rather than the rewrite's output directly).

### 15.3 Dependency wiring (`src/api/dependencies.py`)
`get_query_rewriter()` follows the same lightweight pattern as `get_retriever()` — a plain function calling `get_llm_client()` directly rather than routing through `Depends()` for its own internals. `get_query_engine()` takes `query_rewriter: QueryRewriter = Depends(get_query_rewriter)` and passes it through to `QueryEngine`.

### 15.4 Tests
`tests/unit/test_query_rewriter.py` (new) — happy-path rewrite, passthrough-when-already-specific, `temperature=0.0`, history formatting (role labels, tool-message exclusion, no-prior-turns placeholder), and fallback behavior (malformed JSON, missing/empty/non-string field, timeout, LLM exception) — all via `MockLLMClient` plus two file-local stubs (`SlowLLMClient`, `ErrorLLMClient`) not added to `conftest.py`, since they're single-purpose to this file. `tests/unit/test_engine.py` — `make_engine()`'s helper updated with a required `rewriter` parameter (defaulting to a new file-local `PassthroughQueryRewriter` stub), since `QueryRewriter` becoming a required `QueryEngine` constructor argument would otherwise break all nine pre-existing tests in the file; four new tests cover round-0 substitution, original-message persistence, call-ordering (rewrite runs before the current turn is appended to history), and non-leakage of the substitution into later tool-calling rounds.

### Decisions made
- **Unconditional, passthrough-by-default rewriting, not reactive-on-low-similarity.** No similarity-score signal currently reaches `engine.py` — it's consumed inside `retriever.py`/`tool_dispatcher.py` and flattened into a JSON string before the LLM sees it, so gating on it would mean new plumbing for a fairly blunt signal. More fundamentally, a low similarity score can't distinguish "query was vague" from "topic isn't in the corpus" — both look identical from the score alone, so reactive rewriting risks burning a wasted tool round (out of only `max_tool_rounds`) diagnosing the wrong problem. Always invoking the rewriter, with the prompt itself deciding whether a rewrite is warranted, avoids both issues at the cost of one extra cheap LLM call per turn.
- **Transient substitution, never persisted.** The rewritten text is swapped into the outgoing LLM message list for round 0 only; `session.messages` — which doubles as the conversation transcript returned by `GET /chat/{session_id}/history` — always keeps the user's literal wording. Persisting the rewrite instead was considered and rejected: it would show the user text they never typed, and would let any single imperfect rewrite compound into the ground truth every future turn's rewrite step builds on. Both `chat.original_query` and `chat.rewritten_query` are captured on the `chat` span regardless, so nothing is lost for analysis purposes — it's just telemetry rather than conversational state.
- **Rewrite timeout is independent and configurable, and never fails the turn.** `QueryRewriter` takes its own `timeout_seconds` (constructor parameter, default `QUERY_REWRITE_TIMEOUT_SECONDS = 15.0`, separate from `engine.py`'s `LLM_REQUEST_TIMEOUT_SECONDS = 60.0`) and falls back to the original message on timeout rather than raising `LLMTimeoutError` the way the main answer-generation and synthesis calls do — deliberate asymmetry, since a slow rewrite should degrade gracefully (skip the optimization) rather than fail a request that could otherwise succeed. Configurability mirrors `SpeakerResolver`'s `window_ms`/`padding_ms` pattern and was added specifically so timeout-fallback tests don't have to wait out a real 15-second clock.
